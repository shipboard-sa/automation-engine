Your Router Already Knows Who's Aboard

Lee Hutchins and Claude · SV Unladen Swallow 2 · November 2026

Presence awareness is one of the most useful signals a boat automation system can have. Your Wi-Fi router already tracks every connected device. One authenticated API call gives you a reliable aboard/ashore boolean for each crew phone — and that boolean gates security rules that would otherwise need manual arming.

What Presence Awareness Enables

A sailboat at a dock or on the hook faces a basic question: is anyone aboard right now? The answer unlocks a tier of automatic behavior that would be intrusive or unsafe without it:

  • Away deterrents. Nobody aboard for ten minutes → cameras arm, a greeting plays if someone steps onto the stern. The slip fence and anchor watch stay armed independently (they follow the mode tap, not presence), but the response escalates when nobody is there to respond in person.
  • Doorbell. Crew aboard during the day, someone on the stern → a quiet notification and a snapshot, not a siren. If the companionway is closed and the A/C running, you cannot hear someone calling from the dock. Presence plus mode plus time of day picks the right response.
  • Anchor-box gate. The touchscreen anchor box can tap DOCK and MOTOR, but it cannot end a secured mode (DOCK → another, or ANCHOR → another) unless a crew phone is aboard. The box has no PIN; presence stands in for it. Without this gate, a stranger at the nav station could silence the theft fence.
  • Night-watch escalation. Crew aboard, night watch armed, intruder on the stern → EMERGENCY. Presence confirms you are asleep, not ashore.

Presence and mode are separate axes. Walking up the dock to the chandlery does not change the boat from DOCK to AWAY, so the slip fence stays armed while the away deterrents arm on top. Returning does not disarm anything either — it just ends the away state. Each axis does its own job.

What presence does not gate: the dinghy alarm loop is armed only by its own physical switch, never by presence or mode. Ashore, the dinghy is usually how you got there — there is nothing on the loop to guard.

The Signal

Each crew member's phone produces one boolean signal: crew.lee_cell, crew.brownie_cell. The rules engine checks it every 30 seconds. A phone that answered within the last ten minutes reads True (aboard). One that has not answered in ten minutes reads False (ashore). For the first ten minutes after the engine starts, the signal is Unknown — treated as not-aboard so that a restart does not briefly drop the away deterrents.

The ten-minute window exists because phones doze. A modern phone in a pocket or on a charger may not respond to every probe. The window is long enough that at least one successful check lands during a normal doze cycle, but short enough that presence tracks reality within a reasonable delay.

Limits the crew accepts: Wi-Fi reaches the dock, so a phone at the marina office counts as aboard. A phone left on the charger while you take the dinghy ashore counts as aboard. A dead phone or one with Wi-Fi off reads as ashore. These are known trade-offs — the signal is useful, not perfect.

How to Get It

Every Wi-Fi router tracks connected clients. The question is whether yours exposes that list through an API. If you are running the stock Starlink router — and most cruisers are — you are in good shape. The Starlink router exposes a gRPC API at 192.168.1.1:9000 with a WifiGetClients method that returns every connected device including its IP address, MAC address, and an active flag. That is everything the presence pattern needs. We have not tested it ourselves (our Starlink runs in bypass mode behind a GL.iNet), but the protobuf definitions in the open-source starlink-client library confirm the fields are there. If you run a third-party router behind Starlink in bypass mode (typically for a boat-level VPN or cellular failover), your router’s own API applies instead.

If your router does expose a client list, the pattern is simple:

  1. Reserve each phone's IP via DHCP. Most router admin pages have a DHCP reservation list: tie each phone's MAC address to a fixed IP. This makes the phone identifiable by IP rather than by MAC, which is important because modern phones randomize their MAC address by default.
  2. Authenticate to the router's API. This varies by router. Some use a session cookie, some use bearer tokens, some use challenge-response. You need the admin password.
  3. Call the client-list endpoint. One call returns every connected device with at least an IP and an online/offline flag.
  4. Match by IP. If the phone's reserved IP appears with online: true, mark it as seen. Apply the window logic.

If your router does not expose an API, or the password is not available, the fallback is the ARP table: read /proc/net/arp on a Linux host and send a UDP probe to each phone's discard port (port 9) to force an ARP resolution. This works but is less reliable for dozing phones, because the kernel's ARP cache expires entries that do not answer the probe.

Worked Example: GL-X3000

The GL.iNet GL-X3000 (Spitz AX, firmware 4.x) exposes a JSON-RPC API over HTTPS on port 443. Authentication is challenge-response: the router sends a salt and nonce, the client computes a hash, and the router returns a session ID.

# 1. Request a challenge
POST https://192.168.8.1/rpc
{
  "jsonrpc": "2.0", "id": 1,
  "method": "challenge",
  "params": {"username": "root"}
}
# Response: {"result": {"alg": 5, "salt": "...", "nonce": "..."}}

# 2. Compute the login hash
hashed  = crypt(password, "$5$" + salt)   # SHA-256 unix crypt
payload = username + ":" + hashed + ":" + nonce
hash    = sha256(payload)

# 3. Log in
POST /rpc
{
  "jsonrpc": "2.0", "id": 2,
  "method": "login",
  "params": {"username": "root", "hash": "<computed>"}
}
# Response: {"result": {"sid": "abc123..."}}

# 4. Fetch the client list
POST /rpc
{
  "jsonrpc": "2.0", "id": 3,
  "method": "call",
  "params": ["abc123...", "clients", "get_list", {}]
}
# Response: {"result": {"clients": [
#   {"name": "Lee-iPhone", "ip": "192.168.8.50",
#    "mac": "aa:bb:cc:dd:ee:ff", "online": true},
#   ...
# ]}}

The session ID is valid for about an hour. If a call returns error code -32000, the session expired; re-authenticate and retry. The clients.get_list call returns every device the router has seen, with online: true for those currently connected. Match each client's ip against your crew list. One call covers all phones — no per-device polling.

Firmware note: on the GL-X3000 firmware we tested, clients.get_list was the only working client-list endpoint out of twelve we tried. Others returned -32601 (method not found). If your GL.iNet model behaves differently, try clients.get_list first.

Adapt to Your Router

The pattern is the same regardless of router. The authentication and endpoint change; the presence logic does not.

RouterClient-list methodAuth
Starlink (stock) gRPC WifiGetClients at 192.168.1.1:9000 — returns ip_address, mac_address, active per client None (unauthenticated local)
GL.iNet JSON-RPC clients.get_list at 192.168.8.1/rpc (the worked example above) Challenge/response (admin password)
OpenWrt ubus call hostapd.wlan0 get_clients (via uhttpd-mod-ubus or SSH) ubus session token or SSH key
Any (fallback) /proc/net/arp on the automation host None (local read)

For any router with an API: wrap the auth and the call in a small client class, expose a get_online_ips() -> set[str] method, and plug it into the same window logic. The presence adapter does not need to know which router it is talking to once the client list arrives. The Starlink gRPC endpoint is unauthenticated on the local network, which makes it the simplest to integrate.

If your router has no API at all, the ARP fallback still works. It is less reliable for phones that doze aggressively, because a phone that ignores the UDP probe drops out of the ARP table after a few minutes and looks like it left. The ten-minute window papers over most of these gaps, but expect occasional false negatives on older Android devices with aggressive battery optimization.

The total cost of this capability is zero hardware and about 150 lines of code. The router was already there. The phones were already connecting to it. All you did was ask.
